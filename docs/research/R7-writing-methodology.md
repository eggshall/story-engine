# R7 写作方法论：可引用来源与授权边界 + 规则/风格指南工具先例 + 规则条款编译框架

> 调研日期：2026-10-11
> 用途：为「作者主写、AI 辅助」的小说写作工作站设计「方法论/培训材料入库 → 可检验规则条款」承接方案。
> 一句话结论：**网文培训材料的「原文」几乎全部不可入库分发，但其「方法论抽象」（套路名、节奏阈值、钩子结构）不受版权保护，可被编译为原创规则条款。成熟工具（Sudowrite/Novelcrafter）只有「自由文本 style guide」，没有「结构化可检验规则 schema」——这正是本工作站可以做差异化的空白。**

## 一、写作方法论的公开可引用来源与授权边界

### 1.1 授权边界总原则（先读这个）

| 材料形态 | 是否可入库/分发 | 依据 |
|----------|----------------|------|
| 方法论**思想、套路名称、节奏概念**（黄金三章、章末留钩、信息释放、毒点） | ✅ 可自由抽象为规则条款 | 著作权法「思想/表达二分」：思想、方法、规则、系统不受版权保护，只有「具体表达」受保护 |
| 官方**新闻稿 / 免费博客** | ⚠️ 可引用/概述（需注 URL），原文转载需授权 | 注明出处即可合理引用 |
| 平台官方**专栏文章 / 课程逐字稿 / 付费课程内容** | ❌ 只能作者个人参考，**不得入库分发** | 版权归平台/作者；付费内容另有合同约束 |
| 公版书（作者逝世满 50 年） | ✅ 可采集（与培训内容无关，仅对文学文本适用） | 中国著作权法第 23 条 |

> 关键区分：把「起点说：开篇前三章要有冲突」编译成规则条款「开篇 3000 字内必须出现冲突事件关键词」——规则条款是**你的原创抽象**，不是对原文的复制，不受原文版权约束。**逐字搬运原文段落才是侵权。**

## 二、成熟工具的「写作规则 / 风格指南」实现先例

### 2.1 Sudowrite Story Bible —— 有 Style 字段，但是「自由文本」不是「结构化规则」

- 官方文档「What is Story Bible」：https://docs.sudowrite.com/using-sudowrite/1ow1qkGqof9rtcyGnrWUBS/what-is-story-bible/jmWepHcQdJetNrE991fjJC
- 官方博客「Story Bible Template」：https://sudowrite.com/blog/story-bible-template/

**字段链**：Braindump → **Genre → Style** → Synopsis → Characters → Worldbuilding → Outline → Scenes → Draft。
- **Style 字段确实存在**，且「直接同时影响 Draft 中的 Beat 生成与 Prose 生成」。
- 但 Style 是**自由文本字段**（官方原话："Style — your voice, your rules"），**没有结构化的 rules/constraints/banned-words schema**。规则写多写少、写成什么样全靠用户自己。
- **结论**：Sudowrite 有「风格指南」的存放位置，但没有「可检验规则条款」的数据结构。它把 style 当「prompt 上下文」用，不当「校验器」用。

### 2.2 Novelcrafter —— style guide Codex 条目 + 自定义 prompt 库

- Style guide Codex 条目官方课：https://www.novelcrafter.com/courses/codex-cookbook/effective-style-entries
- Prompt 函数参考：https://www.novelcrafter.com/help/reference/prompts/prompt-functions
- 术语表：https://www.novelcrafter.com/help/reference/terms/novelcrafter

**style guide 条目官方建议包含的组件**（直接对应规则字段）：
1. Narrative voice preferences（叙事声线偏好）
2. Description style（描写风格）
3. Dialogue handling（对话处理）
4. **Technical requirements（技术要求）**
5. **Content presentation rules（内容呈现规则）**
6. **Specific do's and don'ts（明确的该做/不该做清单）**

**关键发现**：Novelcrafter 是**唯一官方把「do's and don'ts」「内容呈现规则」作为 style guide 一级组件列出的工具**——这最接近「规则清单」形态。但它同样是**自由文本条目**，靠 Codex 检索注入 prompt，**没有机器校验**。官方还明确警告：「规则写太多会机械化/文风僵硬，要给灵活性留边界（如"动作场景用短句"而非"所有句子必须 15 字以内"）」。

### 2.3 结构化「禁词/偏置」机制先例（比 style guide 更接近规则引擎）

| 工具 | 机制 | URL | 说明 |
|------|------|-----|------|
| NovelAI | **Banned Tokens**（完全禁止某 token 生成）+ **Phrase Bias**（短语偏置：{curly braces}=精确文本，[square brackets]=token ID，大小写敏感） | https://docs.novelai.net/en/text/editor/advancedsettings | **这是「禁词表」最硬核的结构化实现**：直接作用于 token 采样层，不是 prompt 建议。上限 2048 条 ban / 1024 条 bias（官方 X 公告 https://x.com/novelaiofficial/status/1490415583271260162 ） |
| NovelAI | Stop Sequences + Min Output Length | 同上 | 结构化的「停止序列」控制 |

**启示**：禁词/毒点词的「硬禁」在业界有成熟先例（NovelAI 采样层 ban），本工作站可用「生成后正则校验 + 命中定点重写」等效实现，且更可控。

### 2.4 「平台写作规范结构化入库」的先例 —— 未发现公开先例

- 检索「网文平台写作规范 结构化 规则工具」无公开结果。
- **诚实结论**：目前**没有公开工具把起点/番茄等平台的写作规范（黄金三章、章末钩子、信息释放节奏）做成结构化、可机器校验的规则库**。行业最接近的是：
  1. NovelAI 的 Banned Tokens（只有「禁词」这一维，无节奏/结构维度）；
  2. 民间「拆书」实践（知乎 https://www.zhihu.com/question/665537425/answer/1983161648605861099 —— 把章末钩子手法分类记录）——**手动、无工具化**。
- **差异化机会**：本工作站把「网文方法论 → A/B/C 三层可检验规则」是**增量创新**，无现成竞品可抄，需自建 schema（详见第三节）。

## 三、把方法论编译成「可检验规则条款」的分类框架（核心交付）

### 3.0 分类依据：判定器是什么

- **A 类「可自动检验」**：判定器 = 纯 Python（正则 + jieba + 统计），无需 LLM。落地为 `metrics.py` / `drift.py`（本项目已有 17 项纯 Python 指标）+ 伏笔账本状态机。
- **B 类「半可检」**：判定器 = 本地小模型（gm4，结构化 JSON 抽取实测胜出）当判官，强制输出 `{等级, 命中条款, 理由}`。
- **C 类「只能做提示」**：无判定器。只能作为生成前注入（style_prompt / 规则提示块）+ 人工判断。

> 项目内已有实现对应：A 类 → `src/story_engine/style/metrics.py`（17 项）+ `drift.py`（warn/alert 分级）+ 伏笔 ledger（planted→developed→payed_off/abandoned）；B 类 → 本地 gm4 判定；C 类 → `style_prompts` 生成前注入。本表即「把培训材料编译进这三层」的模板。

### 3.1 A 类「可自动检验」样例条款（8 条）

| # | 规则名 | 触发场景 | 判定方式（纯 Python） | 违反时怎么办 |
|---|--------|----------|----------------------|--------------|
| A1 | 章末钩子检测 | 每章结尾（末 ~200 字） | 正则匹配悬念词表（然而/但是/就在这时/突然/竟然/却/难道…）+ 疑问句检测 + 未闭合悬念（"他想起了…"类） | 无钩子 → alert「章末无钩子」，建议补一句悬念/留白 |
| A2 | 开篇冲突入局 | 首章开头 | 统计开篇 N 字（如 3000 字）内是否出现冲突/异常事件关键词（打斗/追杀/穿/重生/系统/退婚/觉醒…，题材词表可配） | 超出阈值 → warn「开篇铺垫过长」，建议前移冲突 |
| A3 | 对话占比 | 全章 | 引号内字数 / 总字数，与作者滚动基线（前 10 章中位数）比较 | 偏离 ±2σ → alert（比例失衡）；±1σ → warn |
| A4 | 段落长度 | 全章 | 平均段落字数 + 超长段（>N 字）比例 + 单句段比例 | 超长段过多 → warn「段落臃肿，建议拆分」 |
| A5 | 视角一致性 | 全章 | 人称代词分布（我/你/他/她）滚动基线突变检测 | 视角漂移 → alert，定位漂移段落 |
| A6 | 禁词表 / AI 味 | 全章 | 正则匹配禁词（AI 味：然而/值得注意的是/不可否认/从某种角度；毒点词：降智/圣母/无脑…） | 命中 → 定点重写命中句（非整章重写） |
| A7 | 伏笔回收 | 全书 | 伏笔账本状态机：planted → payed_off/abandoned；超阈值未回收 | 报「未回收伏笔」清单（区分 intentional_reveal vs plot_hole） |
| A8 | 感叹/疑问句比例（节奏） | 全章 | 感叹句比例、疑问句比例，近零指标用绝对容差 | 偏离容差 → warn/alert（节奏异常，参照 drift 分级规则） |

### 3.2 B 类「半可检」样例条款（7 条，LLM 判官 + 结构化 JSON）

| # | 规则名 | 触发场景 | 判定方式（本地 gm4 判官） | 违反时怎么办 |
|---|--------|----------|--------------------------|--------------|
| B1 | 信息释放节奏 | 每章 | LLM 读章判「信息密度是否过载/过慢」，输出 `{等级: 过快/合适/过慢, 理由}` | 过载 → 建议拆章/延后信息点；过慢 → 建议前移爆点 |
| B2 | 人物动机充分性 | 关键转折（主角重大决定/反水/牺牲） | LLM 判「该行为是否有前文铺垫动机」，输出 `{充分/不足, 缺哪类铺垫}` | 不足 → 提示在更早章节补伏笔/心理铺垫 |
| B3 | 章末钩子强度 | 每章结尾 | LLM 判「钩子强度 1-5 分 + 类型（悬念/反转/期待）」（A1 只判有无，B3 判强弱） | 低分 → 建议强化钩子（升级悬念/制造反差） |
| B4 | 人物行为 OOC | 全章 | LLM 对照角色卡判「行为是否符合人设」 | OOC → 提示修正或调整角色卡 |
| B5 | 冲突升级是否到位 | 章内/章间 | LLM 判「本章冲突相对前章是升级/持平/回落」 | 连续回落 → warn「节奏泄气」，建议加对抗强度 |
| B6 | 伏笔埋设自然度 | 新埋伏笔处 | LLM 判「埋设是否刻意/突兀」（账本只查回收，B6 判埋设质量） | 突兀 → 提示改自然（藏进对话/细节） |
| B7 | 套路/毒点识别 | 全章 | LLM 判「是否命中典型套路/毒点」（降智操作、无脑反派、强行误会…），输出命中列表 | 命中 → 提示替换套路化处理 |

### 3.3 C 类「只能做提示」样例条款（6 条）

| # | 规则名 | 触发场景 | 判定方式 | 违反时怎么办 |
|---|--------|----------|----------|--------------|
| C1 | 文笔好坏 | 全局 | 无法自动判定 | 生成前注入风格提示 + 作者人工判断 |
| C2 | 情感浓度/张力 | 关键情感场景 | 无法自动判定 | 生成前提示目标情绪基调 |
| C3 | 幽默/笑点质量 | 喜剧场景 | 无法自动判定 | 生成前提示 + 人工判断 |
| C4 | 意象/象征深度 | 全局 | 无法自动判定 | 生成前提示（如 Truby 的 symbol web 概念） |
| C5 | 语言高级感/文采 | 全局 | 无法自动判定 | 生成前注入 style_prompt + 样段 few-shot |
| C6 | 读者爽感 | 全局 | 无法自动判定 | 生成前提示爽点节奏，发布后看数据反馈 |

### 3.4 条款落点：生成前提示 vs 生成后校验 vs 两者

| 类别 | 生成前提示（注入 prompt） | 生成后校验（规则引擎） | 落地位置 |
|------|--------------------------|------------------------|----------|
| **A 类** | 仅「禁词表」值得前置（告诉 AI 别写这些词）；其余**不需要**（规则引擎会查） | **主落点**：写后跑 `metrics.py`/`drift.py`，warn/alert 分级，超阈值定点重写 | `style/metrics.py` + `drift.py` + 伏笔 ledger |
| **B 类** | **建议两者都要**：先提示「遵循该条款」降低违规率 | **主落点**：写后本地 gm4 判定，结构化 JSON 回传 | `style/drift.py` 扩展 + 本地判官路由（gm4） |
| **C 类** | **唯一落点**：生成前注入（style_prompt + 样段 few-shot） | 无（无判定器，只能人工） | `style_prompts` 注入链路（`render_style_block`） |

**落地原则（结合项目已有架构）**：
- **A 类硬门禁**：作者主写时，A 类是「结构备忘 + 写后自检」，不是审批闸门（作者主写模式下闸门从 5 道收敛为 3 道）。
- **B 类异步**：本地 gm4 判官是离线批处理活，**必须与交互式写作串行排队**（16GB 卡并发会爆），不能阻塞光标处写作。
- **C 类即风格块**：直接复用 `render_style_block(profile)` 的三段式注入（风格总结 + 量化特征 + 原文样段），把「培训材料抽象出的风格建议」写成 profile 即可。
- **规则条款本身是原创抽象**，不受原文版权约束——这是「培训材料不可入库、但方法论可入库」的法律落点。

### 3.5 编译工作流（把一份培训材料变成规则条款）

```
培训材料/方法论长文
   ↓ ① 抽取「可检验主张」（把"开篇要有冲突"→ 命题化）
   ↓ ② 分类：能否用正则/统计判定？ → A；能否让 LLM 结构化判定？ → B；都不能 → C
   ↓ ③ 落表：规则名 + 触发场景 + 判定方式 + 违反动作（本表模板）
   ↓ ④ 落地：A→metrics.py 指标；B→gm4 判官 prompt；C→style_prompt 注入
```

> 每条条款必须带**可测阈值**（"开篇 3000 字内出冲突"），否则它就不是「可检验条款」，只是「建议」——这是与 Sudowrite/Novelcrafter 自由文本 style guide 的本质区别。

---

## 四、核心结论（8-12 条）

1. **法律分界清晰**：网文培训「原文」（专栏/课程/视频）几乎全部不可入库分发；「方法论抽象」不受版权保护，可编译为原创规则条款——这是整个方案的合法性基础。
2. **国内四大可读源**：阅文作家专区 write.qq.com、中国作家网（公开可引用）、番茄作家助手作家课堂（平台内受限）、知乎/公众号长文（受限），方法论思想均可学习、原文均不可入库。
3. **国外四大方法论**：Story Grid、Save the Cat（15 beats 公开可引用）、John Truby 22 步（书籍受限/概述公开）、K.M. Weiland（免费博客公开可引用）。
4. **Sudowrite 有 Style 字段但无规则 schema**：Story Bible 的 Style 是自由文本（"your voice, your rules"），当 prompt 上下文用，不当校验器用。
5. **Novelcrafter 最接近「规则清单」**：官方把 do's and don'ts / 内容呈现规则列为 style guide 一级组件，但仍是自由文本、靠检索注入、无机器校验。
6. **NovelAI 是「禁词」硬核先例**：Banned Tokens 直接在采样层禁 token + Phrase Bias 短语偏置，是结构化禁词表的业界标准实现。
7. **「平台规范结构化入库」无公开先例**：业界只有禁词一维（NovelAI）+ 手动拆书实践；把黄金三章/章末钩子/信息释放做成可校验规则库是增量创新，需自建 schema。
8. **A 类规则靠纯 Python**：章末钩子、开篇冲突、对话占比、段落长度、视角一致性、禁词表、伏笔回收、感叹/疑问句比例——项目 `metrics.py` 已有 17 项指标可承接，只需补「钩子检测」「伏笔状态机」两项。
9. **B 类规则靠本地 gm4 判官**：信息释放节奏、人物动机、钩子强度、OOC、冲突升级、伏笔自然度、套路/毒点——强制结构化 JSON 输出，且必须串行排队不阻塞写作。
10. **C 类规则只能提示**：文笔、情感浓度、幽默、意象、文采、爽感——唯一落点是生成前注入 style_prompt + 样段 few-shot。
11. **落点分工**：A 类=生成后校验为主；B 类=生成前提示 + 生成后判官两者都要；C 类=生成前提示唯一落点。
12. **本质区别**：本方案的规则条款带**可测阈值**（"开篇 3000 字内出冲突"），而 Sudowrite/Novelcrafter 的 style guide 是自由文本——「可检验」是本工作站相对成熟工具的差异化能力。
